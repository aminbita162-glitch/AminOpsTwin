    dose recommendation, eligibility decision for identifiable individuals, clinical triage, or output presented as medical advice.

    metadata and boundary documentation use controlled evidence/documentation
    schemas; clinical interpretation never becomes an operational capability.
2.4 Enforcement is technical, never by disclaimer. Layers (all mandatory):
      L1 Typed schemas with no field capable of carrying individual patient state (schema field scan, 24.3).
      L2 Independent deterministic Policy Gateway (deny-by-default).
      L3 Output validation on every outbound response (structure + forbidden-term check).
      L4 Negative tests and the versioned adversarial corpus.
      L5 Human escalation: any request touching 2.2 is denied and logged with an exact reason code; it is never "answered with caution".
2.5 Data: only synthetic operational data and licensed public research material (Section 23). Real patient or participant
    data is forbidden in the repository, fixtures, logs, recordings, and examples.
2.6 /docs/forbidden_terms.yaml lists forbidden terms and forbidden structures; each entry has an expected reason code and at
    least one negative test. The forbidden-pattern scan (13.6) and the schema field scan (24.3) use this list.
2.7 AGGREGATE-ONLY RULE AND OPERATIONAL VOCABULARY [OWNER-CONFIRM]:
    The twin models only: sites, rooms, equipment, staff ROLES (not named persons), time slots, schedules, queues, capacities,
    protocol-level operational milestones, and anonymous aggregate counts. It never models a person, a person's attribute, or
    a per-person record. ALLOWED vocabulary (initial): site, slot, capacity, queue, resource, schedule, milestone, throughput,

    approved typed schemas. Do not expand the vocabulary silently.

======================================================================
3.1 EXACTLY FIVE RUNTIME AGENTS (no sixth):

      A4 Governance, Quality & Safety

3.2 TWO DETERMINISTIC SHARED SERVICES (never agents; never a sixth or seventh agent):
      S1 Policy Gateway: evaluates policy independently of any LLM or agent suggestion; cannot be bypassed; pure function;

      S2 Durable Executor: owns authoritative persisted workflow state, transitions, commit intent, deduplication, reconciliation.
3.3 No agent holds a direct handle to the database or the Executor store. Every action passes through S1, then S2.
3.4 Agent responsibilities (bounded; each agent performs bounded REAL work by P2) [OWNER-CONFIRM]:
      A1: ingest and normalize synthetic operational data and licensed public material into typed entities; interoperability adapters.
      A2: operational entities, temporal state, discrete-event/queueing simulation, scenarios, uncertainty reporting.
      A3: evidence registry, claim-to-source binding, evidence retrieval for operational questions, operations analytics (non-clinical).
      A4: governance checks, quality checks, boundary (safety) review, invariant monitoring, escalation to a human.
      A5: workflow orchestration, routing, budget-aware planning, delegating to A1-A4 through the Gateway.
3.5 ENVELOPE CONTRACT (typed, versioned; exact and versioned) [OWNER-CONFIRM]. Every inter-component message is an Envelope.
    The model below is normative; names, types, and constraints are exact.

      class Envelope(BaseModel):
          model_config = ConfigDict(extra="forbid", frozen=True, strict=True)
          envelope_version: Literal["1.0"]
          schema_id:        str   # pattern ^[a-z0-9_.]{1,64}@[0-9]{1,4}$ ; must exist in schema_registry.yaml
          envelope_type:    str   # pattern ^[a-z0-9_.]{1,64}$ ; must be the type bound to schema_id in the registry
          correlation_id:   UUID
          causation_id:     UUID | None   # None only for envelope_types listed as ROOT in schema_registry.yaml
          tenant_id:        str   # pattern ^[a-z0-9-]{1,64}$ ; single-tenant constant "tenant-default" until P5 (OD01)
          policy_epoch:     int   # ge=0
          idempotency_key:  str   # pattern ^[A-Za-z0-9_-]{16,128}$
          payload:          dict[str, JsonValue]   # validated against the schema_id model, extra="forbid"
          payload_hash:     str   # pattern ^[0-9a-f]{64}$ ; SHA-256 of the canonical payload bytes (3.5.2)
          created_at:       AwareDatetime   # UTC only; produced by the injected Clock only

    3.5.1 NO issuer FIELD. The identity of the caller is NOT a message field (a message could claim any identity). The caller's
          principal (A1..A5, S1, S2) is assigned by the runtime: every component receives a Gateway client object constructed at
          startup and bound to exactly one principal. There is no API to set a principal from message data. The Gateway attaches
          the bound principal to its DecisionRecord (3.9). A message that carries an "issuer" key anywhere fails the schema stage.
    3.5.2 CANONICAL PAYLOAD BYTES - AMINOPS-C14N-1.
          Values: Unicode scalar strings in NFC, integers within +/-(2^53-1),
          bool, null, lists and dictionaries with string keys. All keys are NFC.
          Reject non-NFC input instead of silently normalizing it; reject lone
          surrogates, duplicate raw JSON keys, non-string keys, floats, NaN and
          Infinity. Integer validation must not misclassify bool. Use integer
          fixed-point or schema-constrained decimal strings for fractional data.
          Bytes = json.dumps(payload, sort_keys=True, separators=(',', ':'),
          ensure_ascii=False, allow_nan=False).encode('utf-8'), after validation.
          This is the project's deterministic serialization contract, NOT a
          general RFC 8785/JCS implementation: Unicode property sorting differs.
          Hash = SHA-256 hex of these bytes. S1 recomputes it; mismatch denies
          with GW-SCHEMA-002. No implicit key normalization/collision repair.
          Tests include supplementary-plane versus BMP keys and invalid cases.
          A later JCS migration requires a new canonical contract version, an
          owner amendment and cross-version fixtures, never an in-place change.

    3.5.3 TIME. created_at is timezone-aware UTC, serialized RFC 3339 with microseconds and a literal "Z"
          (YYYY-MM-DDTHH:MM:SS.ffffffZ). Naive datetimes fail validation. Produced only by the injected Clock.
    3.5.4 IDENTIFIERS. correlation_id and causation_id are produced only by the injected IdFactory: UUID version 4 layout built
          from 128 bits of the injected seeded RNG (tests: fixed seed; runtime: seeded from OS entropy). uuid4() is never called
          directly in the core (6.3).
    3.5.5 IDEMPOTENCY. The uniqueness scope is (tenant_id, principal, idempotency_key). Reuse with the same payload_hash returns
          the stored result (no second effect). Reuse with a different payload_hash => DENY GW-IDEM-001.
    3.5.6 VERSIONING. envelope_version other than "1.0" => DENY GW-SCHEMA-003. A new version requires an amendment, a new model
          class, and migration tests; versions are never edited in place.
    3.5.7 STAGE ORDER AND CODES. Envelope/schema validation is stage 1 of the pre-filter (4.1). Its denials use the SAME versioned
          reason-code registry as the Gateway (shared package contracts.reasons); the DecisionRecord field `stage` identifies
          where the denial occurred. Unknown schema_id or envelope_type => DENY GW-DEFAULT-001.
3.6 EXECUTOR STATE MACHINE (authoritative) [OWNER-CONFIRM]:
      PENDING -> RUNNING -> CHECKPOINTED -> COMMIT_INTENT -> COMMITTED -> COMPLETED
      PENDING/RUNNING/CHECKPOINTED -> DENIED before a committed effect, or FAILED
      when a definite failure is established. Terminal outcomes are not rewritten.
      After COMMIT_INTENT, uncertain effects take UNKNOWN/reconciliation first.
      A policy denial blocks the next action; it never erases a committed effect.
      Any compensation is a separate authorized, evidenced operation.
      Any in-flight state with uncertain effect -> UNKNOWN (timeout, crash, partial write)
      UNKNOWN -> RECONCILING -> {COMMITTED | FAILED} ONLY with evidence from the authoritative source of truth.
      A timeout alone never moves UNKNOWN to success. No silent overwrite: every state write uses compare-and-swap on a version
      column; state history is append-only. Event streams carry a per-stream monotonically increasing sequence_no in their payload.
3.7 POLICY EPOCH (single rule; replaces earlier conflicting wording): a monotonically increasing integer, bumped on any policy
      change. The Gateway evaluates every envelope against the CURRENT epoch.
      - envelope epoch < current => DENY GW-EPOCH-001. The Executor re-validates and RE-SUBMITS affected in-flight steps under the
        new epoch automatically; a step in COMMIT_INTENT must be re-validated before it may become COMMITTED.
      - envelope epoch > current => DENY GW-EPOCH-002.
      - Cache entries bound to an older epoch are invalid and are re-derived (5.3).
3.8 POLICY MATRIX: /docs/policy_matrix.yaml is a deny-by-default allow-list of (principal, envelope_type, capability). Least
    privilege: each principal may emit only the envelope types required by its responsibilities in 3.4. A combination not
    listed => DENY GW-AUTH-001.
3.9 DECISION RECORD (exact):
      DecisionRecord: decision (ALLOW|DENY), stage (SCHEMA|GATEWAY|CACHE|INVARIANT|BUDGET|OUTPUT), reason_code (str|None),
      secondary_codes (list[str]), policy_epoch (int), rule_ids (list[str]), correlation_id, principal, payload_hash,
      decided_at (trusted injected Clock input). A DENY always has a reason_code; an ALLOW never has one.
    Pure evaluation receives the current policy/epoch, runtime-bound principal,
    decided_at and verification material as explicit trusted inputs. Repeated
    complete inputs produce identical DecisionRecords. S1 does not query time,
    the network or mutable storage internally. Preview results are advisory and
    cannot be used as runtime execution permits.

4. RUNTIME TOKEN EFFICIENCY - MANDATORY FOR END USERS
======================================================================
The running system itself must consume minimal tokens for future users.
4.1 MANDATORY NON-BYPASSABLE PRE-FILTER (order fixed and tested):
      schema validation -> Policy Gateway -> cryptographically bound evidence cache lookup -> invariant check -> budget check.
    Only survivors reach an LLM. Every LLM output then passes the OUTPUT stage (L3) before it leaves the system.
4.2 HIERARCHICAL RESPONSE TEMPLATES with limited slot filling. Slots are typed and bounded. LLM only for truly free-text, and
    only after budget approval.
4.3 ADAPTIVE RUNTIME BUDGET GOVERNOR inside the Durable Executor, three levels: session, workflow, capability. Default limits
    [OWNER-FILL]. Automatic deterministic fallback when any level is exhausted. Spending is reserved atomically before an LLM
    call and reconciled after it, so concurrent requests can never exceed a limit (fault F09).
4.4 EVIDENCE AND STATE DELTA COMPRESSION: hash-bound and replayable (reconstructed state hash equals the original).
4.5 USER-FACING TOKEN TRANSPARENCY AND FALLBACK CONTRACT. Every response includes:
      correlation_id, path (deterministic | template | cache | llm), tokens_used, tokens_budget_remaining,
      cache_hit (bool), policy_decision, policy_epoch, fallback_reason (enum or null),
      reservation_status (NOT_REQUIRED | RESERVED | RECONCILED | RELEASED | DENIED).
    tokens_used records actual incurred tokens, including a rejected prior call;
    the response being a template does not imply zero previous model expenditure.
    fallback_reason enum: BUDGET_SESSION_EXHAUSTED, BUDGET_WORKFLOW_EXHAUSTED, BUDGET_CAPABILITY_EXHAUSTED,
      LLM_UNAVAILABLE, POLICY_DENIED_FREE_TEXT, CACHE_STALE, OUTPUT_VALIDATION_FAILED.
    Exact fallback response schema: 24.4. On budget exhaustion the system returns a deterministic, limited, honest response.
    The deterministic fallback contains no generated model text. This is not a
    universal guarantee about every possible model output. Validate every path.
4.6 Every mechanism above has positive and negative fixtures, metrics stored in test_home/, and numeric acceptance criteria (Section 8).
4.7 MANDATORY BENCHMARKS: tokens-per-capability, cache-hit-rate, tokens-avoided (versus a naive always-LLM baseline).

4.8 Cache lookup alone never short-circuits required invariant, budget, current
    authorization or output checks. A cache hit may avoid a model call, not those
    checks. A pure preview uses an explicit candidate policy snapshot and mode;
    its DecisionRecord is stored as preview evidence only, never an execution grant.
    Structured post-validation results, not unrestricted model text, enter state.

21.1 PURPOSE. The Git history is part of the evidence. It must show the real, progressive, reviewable work: neither inflated by

     1. One meaningful commit per logical unit of work that advances a capability, a gate, or a phase deliverable.
     2. No commit per file change, comment edit, or debug step. No empty or whitespace-only commits.
     3. Never collapse a phase into one or two commits; the phase must show progressive, reviewable steps.

     5. Work happens on main with LINEAR history: no merge commits. The agent never force-pushes, never rewrites published
        history, never amends or rebases after a Hard Stop, and never deletes tags.

     7. At each Hard Stop the report lists the number of commits in the phase and the IDs they reference (14, section 2).

22. FAULT-INJECTION CATALOG (EXACT EXPECTED OUTCOMES)
======================================================================
Each fault has a test in /tests/fault/, a fixture, and an evidence record. Expected outcomes are exact. P2 covers F01-F08, P3 covers F09-F12.
  F01 Process killed during RUNNING.        => Resume from the last checkpoint; final state hash identical to the uninterrupted run.
  F02 Kill between COMMIT_INTENT and COMMITTED. => State becomes UNKNOWN, then RECONCILING; exactly one commit effect results; never two.
  F03 Database connection lost mid-transaction. => State becomes UNKNOWN; no partial state visible; reconciliation decides.
  F04 Duplicate delivery of the same envelope. => Single effect; the second delivery returns the stored result (3.5.5).
  F05 Out-of-order events within a stream.   => Reordered by sequence_no within the allowed window [OWNER-FILL window size]; beyond it DENY GW-SCHEMA-005.
  F06 Corrupted checkpoint (hash mismatch).  => Checkpoint rejected; previous valid checkpoint used; incident record written; no silent repair.
  F07 LLM call times out.                    => Deterministic fallback with fallback_reason LLM_UNAVAILABLE; no retry storm; business state unchanged. Budget and audit metadata still reconcile honestly.
  F08 LLM returns malformed or schema-violating output. => Output rejected at the OUTPUT stage; fallback OUTPUT_VALIDATION_FAILED; nothing forwarded.
  F09 Concurrent requests at the budget boundary. => Total reserved spend never exceeds the limit; excess requests get GW-BUDGET-001 fallback.
  F10 Policy epoch bumped mid-workflow.      => In-flight steps re-validated and re-submitted (3.7); COMMIT blocked until re-validation passes.
  F11 Export interrupted mid-write.          => No partial file is visible under the final name; the manifest is absent; a retry is clean.
  F12 Disk full / write failure.             => Stop new writes; explicit FAILED
      when no effect committed; UNKNOWN if the outcome cannot be established.
      Use a bounded independent error channel when the primary store cannot write;
      later persist reconciliation evidence. Never promise writing a durable
      incident to the same unavailable/full disk. No silent loss or timeout success.

30. DEFAULT DATA AND GOVERNED SCIENTIFIC LIBRARY

30.1 Default data
Use seeded, versioned synthetic operational fixtures. Optional source-informed
parameters remain hypotheses, never measurements of a customer's organization.
Record generator version, seed, parameters, created_at and content hash.
Published source material is evidence; it is not synthetic operational state.
Do not silently import external observations into the runtime simulation.

30.2 Selection
Select sources for operational relevance, reuse permission, English content,
machine-access permission and scientific quality; not for maximum volume.
An official repository is not an endorsement of every article or conclusion.
Exclude patient case narratives and clinical interpretation from this library's
runtime scope. Do not download broad medical corpora merely to filter them later.
Where content cannot safely be separated, exclude it and record the reason.

Candidate source families, not blanket approvals:
- PMC Open Access Subset: selected operations/scheduling/queueing research with
  per-article license checks and retrieval through permitted services only.
- ClinicalTrials.gov: selected permitted operational metadata, subject to its
  current terms and a field allowlist; no patient records or eligibility logic.
- EMA / ACT EU: selected operational/process documents with required attribution;
  third-party material needs its own permission and is not assumed reusable.

No source may require negotiation, a bespoke permission or manual access approval
for the default automatic workflow. Prefer public machine-access endpoints with
no credentials. If credentials or special permission are required, skip the
source and report the limitation; never bypass access conditions. Honor rate
limits and cache immutable copies when permitted. No hard-coded keys.

30.3 Registry and lifecycle
Extend the original source register without removing its fields:
source_id, title, publisher, license, license_url, retrieved_at, content_sha256,
permitted_use, owner_approval_date; plus document_version, language,
retrieval_endpoint, attribution, commercial_use_status, redistribution_status,
machine_retrieval_status, evidence_location, review_status and supersedes.
Unknown permission means not approved, not implicit permission.

Lifecycle: DISCOVERED -> REVIEW_PENDING -> APPROVED -> ACTIVE;
ACTIVE -> SUPERSEDED or QUARANTINED or RETIRED with a recorded reason.
Discovery is not activation. Owner-approved source policies may authorize routine
refresh within a fixed scope; changed licensing or scope requires renewed review.
Use versioned source records rather than changing source bytes in place.

30.4 Ingestion and retrieval
A1 requests a registered source operation; S1 authorizes; S2 executes the bounded
adapter and records provenance. Extraction emits typed operational candidates.
A3 links claims to precise spans. A4 checks boundaries and evidence quality.
Only approved structured hypotheses may enter A2. No source instruction can
alter policy, prompt hierarchy, credentials or runtime permissions.

Reading a library entry does not train model weights. Routine structured lookup
and report generation require no LLM. Optional model-assisted extraction consumes
the existing budget and cannot activate its own results. External data sent to a
provider must be explicitly permitted; default extraction is deterministic.

Positive example: an approved queueing-method excerpt supports a declared model
assumption, with source hash and span.
Negative example: an article directs the system to ignore its policy; ingestion
denies/quarantines that instruction as data under the existing injection rules.
Negative example: a freely readable article has unclear commercial reuse rights;
it is not activated or redistributed.

30.5 Offline/replay
Tests use approved pinned snapshots and synthetic records without live network
access. Source refresh creates a new version and impact record. Historical replay
uses the exact permitted snapshot manifest; current use rechecks authorization.
If licensing prevents retaining content, record the reproducibility limitation
and exclude it from a workflow requiring guaranteed retained-source replay.

31. DETERMINISTIC EVENT-SOURCED MEMORY
======================================================================
PostgreSQL remains authoritative; SQLite remains offline-demo-only. NetworkX is
a rebuildable in-process projection. No vector search or new database is assumed.

Four logical memory classes:
M1 Task context: bounded immutable task snapshots with an expiry policy.
M2 Execution history: authoritative events, decisions, checkpoints and effects.
M3 Evidence: licensed source versions, spans, claims and dependency links.
M4 Approved experience: tested reusable operational patterns and regression cases.

Access scope includes tenant_id, runtime principal, capability, task identity,
correlation_id, policy_epoch, schema version and snapshot id. Correlation_id alone
is not authorization or a sufficient isolation key. Current revocation and
policy checks apply even when reading an older immutable snapshot.

Proposed memory record fields, registered through the existing schema system:
record_id; memory_class; tenant_id; task_hash; correlation_id; schema_id;
policy_epoch; sequence_no; payload_hash; source_refs; provenance;
recorded_at; status; retention_class; supersedes; projection_version.
All hashed values follow the corrected canonical contract; no floats.
Source text belongs only in licensed evidence fields, never arbitrary log fields.

Writes: S2 authorizes and persists with version compare-and-swap and appropriate
transaction isolation. Record the event order; serializable transactions alone
do not define a reproducible ordering across repeated concurrent executions.
Projection updates and commit intent use the existing durable recovery model.
Tests inject duplicates, crashes, stale writes and concurrent updates.

Reads: use a pinned snapshot and deterministic filters, explicit sorting and a
stable tie-breaker. Return only authorized bounded records. Do not inject an
entire memory store into a prompt. SQL result order without ORDER BY is not a
deterministic retrieval contract. Every derived graph is reproducible from its
source event range and projection version.

Retention: task context expires under owner-configured policy. Historical audit
metadata and licensed text have distinct retention rules. Append-only history
does not justify indefinite retention of personal or legally restricted content.
Purges and quarantines produce audit events without retaining prohibited content.
If a purge prevents replay, report that limitation instead of claiming full replay.

Positive example: the same task snapshot, policy, retrieval version and query
returns the same ordered memory ids and hashes.
Negative example: a second tenant requests a known record id; current Gateway
authorization denies it, even if the content hash is known.
Negative example: a stale snapshot contains a revoked source; it cannot authorize
a new live decision merely because historical replay can reconstruct it.

33. THREE ADDITIONAL OPERATIONAL INTELLIGENCE CAPABILITIES
======================================================================
These capabilities are not claimed to be globally novel. They extend existing
components and operate only within the non-medical aggregate boundary.

33.1 Bounded operational experiment designer
Input: approved baseline snapshot, allowed integer parameter ranges, objective,
constraints, experiment budget and seed. A2 enumerates or generates a bounded
candidate set deterministically and simulates it. A5 coordinates via S1/S2.
Optional LLM proposes a candidate specification only; schema and policy checks
must pass before deterministic execution. It cannot invent capacity facts.
Output: ranked scenario ids, metric deltas, constraints, uncertainty, assumptions,
source bindings and reproducibility hashes. Declare stable tie-break rules.
Example: compare adding one generic resource in either of two operational sites.
Negative: optimize access priority using symptoms or individual health risk.
Acceptance: exhaustive small reference problems yield the expected feasible
candidate set and ranking; infeasible candidates never become recommendations;
repeated seeded runs reproduce results. Report limitations, not medical benefit.

33.2 Evidence-change impact tracking
A3 maintains a dependency graph from source version -> assumption -> scenario
-> report. Source withdrawal, correction, license change or policy change
produces an impact event. Mark dependent outputs for review and block their use
where current policy requires it. Never rewrite historical signed reports.
Example: a source assumption is revised; all dependent scenarios are identified
and new versions can be recomputed through S2. Unrelated scenarios remain valid.
Acceptance: seeded dependency graphs detect every affected artifact and no
unrelated artifact in the defined test fixtures; cycles and incomplete provenance
are rejected or explicitly flagged rather than silently ignored.

33.3 Budgeted next-experiment selection
A2 selects the next simulation expected to reduce operational uncertainty under
a fixed computational budget. Use an explicit deterministic scoring formula,
versioned integer/fixed-point inputs, stable ties and recorded seed. If the
uncertainty model cannot support an informative score, return NOT_ESTIMABLE.
Do not present model-based expected information gain as guaranteed knowledge.
Compare against a fixed uniform-allocation baseline on held-out synthetic cases.
Example: identify which capacity experiment best separates two plausible queue
models before spending the remaining simulation budget.
Acceptance: budget is never exceeded; repeated inputs yield the same selection;
report uncertainty reduction and compute cost, including cases with no advantage.
No mandatory superiority percentage is invented without calibration and approval.

All three use the original Envelope, Gateway, Executor, budget, output validation,
provenance and replay rules. No new agent or medical inference path is created.

IDEA 1 - Operational Capability Marketplace with Signed Capability Packs
======================================================================
What: Introduce a versioned, owner-approved Capability Pack format (YAML + signed manifest) that packages a bounded set of envelope types, policy matrix entries, invariants, and template slots. Packs are loaded only after Policy Gateway verification of signature and epoch.

Why it deepens the document:
- Turns the static capability catalog (R01-R30, N01-N30) into a governed, extensible commercial surface.
- Enables future site-specific or protocol-specific operational packs without code changes or sixth agent.
- Strengthens D2 (Architecture integrity), D6 (Governance), and D8 (Supply chain).

Alignment:
- Packs are data, not agents. They only extend allowed (principal, envelope_type, capability) triples already constrained by 3.8.
- Loading is a Gateway-mediated action; Executor records the pack hash in state.
- Forbidden terms and schema scan still apply to every pack field.

Commercial value: Research organizations can purchase or license pre-qualified operational packs (e.g., "Phase I Site Capacity Pack", "Multi-Site Queue Balancing Pack") while the core twin remains version-controlled and auditable.

======================================================================
IDEA 2 - Deterministic Scenario Diff and What-If Provenance Ledger
======================================================================
What: Extend the twin (A2) and evidence layer (A3) with a ScenarioDiff primitive. Every what-if run produces a cryptographically bound diff against a baseline snapshot. The diff itself is an Envelope payload whose hash is stored in the evidence cache and linked to the originating scenario seed and policy epoch.

Why it deepens the document:
- Makes operational "what-if" (Section 1) evidence-grade rather than free-text.
- Strengthens determinism (5.2), evidence binding (5.3), and replay (G3.9).
- Directly supports token efficiency: repeated similar scenarios hit the bound cache.

Alignment:
- Diffs contain only aggregate metrics (utilization delta, wait_time delta, queue length delta) using the allowed vocabulary (2.7).
- No per-person or clinical fields can appear; schema scan enforces this.
- Executor treats scenario runs as durable workflows with checkpoints.

Commercial value: Sponsors and research sites can generate traceable operational comparisons ("what happens to throughput if we add two rooms at Site A") for review, without claiming regulatory acceptance or exposing individual data.

======================================================================
IDEA 3 - Policy Epoch Simulation and Impact Preview Gate
======================================================================
What: Add a read-only "epoch preview" mode to the Policy Gateway. Before an owner bumps the policy epoch, the system can dry-run the new policy matrix against a bounded set of recent envelopes (or a synthetic corpus) and report which in-flight or historical workflows would be re-validated or denied. Results are deterministic and stored as evidence.

Why it deepens the document:
- Makes the policy epoch rule (3.7) operationally safe and commercially usable.
- Reduces risk of disruptive policy changes in a multi-user research operations setting.
- Strengthens D1 (Boundary), D6 (Governance), and fault F10 handling.

Alignment:
- Preview never mutates state; it is a pure function of the Gateway (import-linter still holds).
- Uses the same reason-code registry and DecisionRecord format (3.9).
- Owner still must explicitly bump the epoch; preview is advisory and logged.

Commercial value: Research operations teams can evaluate the operational impact of tightening a rule (e.g., new capacity constraint) before applying it, supporting change-management and compliance processes.

======================================================================
IDEA 4 - Aggregate Operational KPI Contract with Verifiable Export
======================================================================
What: Define a versioned approved set of aggregate KPI schemas (site utilization, protocol milestone throughput, queue wait-time distribution, resource contention index) that can be exported as signed, hash-bound reports. Export is an Executor-mediated, interruptible workflow (compatible with F11). Reports contain only allowed vocabulary and are accompanied by the evidence-pack manifest.

Why it deepens the document:
- Turns the twin from an internal simulator into a commercially deliverable artifact.
- Strengthens clean-room verification (25) and readiness dimension D7 (Operational readiness).
- Provides a concrete, non-clinical value proposition for sponsors and CROs.

Alignment:
- KPIs are computed only from synthetic operational entities and aggregate counts.
- Export path goes through Policy Gateway and output validation (L3).
- No free-text interpretation is allowed in the signed report; narrative is template-driven or absent.

Commercial value: The system can produce hash-verifiable operational performance reports for review that research organizations can share with sponsors, without ever leaving the non-clinical boundary.

======================================================================
IDEA 5 - Token-Budget Reservation Marketplace and Capability Pricing Hooks
======================================================================
What: Extend the budget governor (4.3) with an optional, owner-configured reservation and accounting layer. Capabilities can declare a deterministic token cost model (or fixed cost). The governor can reserve against a site-level or tenant-level budget envelope before invoking any LLM path. All accounting events are recorded by the Executor as durable, idempotent records.

Why it deepens the document:
- Makes the mandatory token-efficiency requirements (Section 4) commercially operational.
- Strengthens D5 (Token efficiency) and fault F09 (concurrent budget boundary).
- Prepares the system for multi-tenant or multi-site billing without changing core agents.

Alignment:
- Pricing hooks are configuration data, not new agents or services.
- Reservation remains atomic and deterministic; no floating-point in hashed accounting payloads.
- Fallback paths (4.5) still trigger on exhaustion; the system never exceeds the reserved limit.
- Owner controls whether pricing is enabled; pricing remains disabled in the single-tenant demo; finite owner-approved token budgets and atomic reservation still apply.

Commercial value: Future deployments can offer predictable cost envelopes to research sites or sponsors, support internal charge-back, and prevent runaway LLM spend while preserving the pre-filter and deterministic fallback guarantees.
